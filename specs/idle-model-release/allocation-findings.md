# Isolated native allocation investigation

The capture is from the newly built release `ssd` with `MallocStackLogging=1`, an isolated `SS_HOME`, `SS_EMBED_PROVIDER=cpu`, lazy startup, and model expiry set to 3600 seconds. The complete environment fields, successful one-file index and actual query result are in [allocation-workload.json](allocation-workload.json). `allocation-ps.txt` records the live command and RSS. Stack logging changes the measurement condition; these samples cannot be treated as the earlier probe's memory measurements.

The large allocated blocks at addresses `0x143cb8000` and `0x108fcc000` are attributed by the live heap to Espresso (`allocation-heap-all-addresses.txt`, beginning at line 34). Their last recorded allocation events are at `allocation-address-stacks.txt:1138` and `:2107`: `Espresso::blob_cpu::resize` → `Espresso::allocate_blobs` → network reshape → `MLNeuralNetworkEngine` plan rebuild → `onnxruntime::coreml::Execution::Predict` → the CoreML execution provider callback → ONNX execution → fastembed. These are execution-plan blobs in this capture; earlier events for the same recycled addresses include compiler weight-loading allocations and frees, so the first stack in an address history must not be mistaken for its live allocation.

`0x118448000` (`allocation-address-stacks.txt:2189`) traces through `onnxruntime::BFCArena::Reserve` → `GemmPackBFp32` → `MatMul<float>::PrePack` → `PrepackConstantInitializedTensors` during session initialization. The full live-allocation grouping is in `allocation-malloc-all.txt:27`; it is not the same quantity as process RSS.

`0x138620000` (`allocation-address-stacks.txt:2233`) traces to proxima telemetry `RingSet::new` during daemon startup, a separate allocation from inference. Other instances appear in `allocation-malloc-all.txt:31`.

`allocation-vmmap.txt:39-43` identifies resident reusable malloc regions and separately lists dirty memory; reusable resident pages should not be described as live model objects. `allocation-heap.txt` reports live heap allocations while `allocation-ps.txt` reports RSS; they are different views of memory with different accounting. Neither alone establishes which memory was freed in the expiry arm.

## Provider discrepancy

The workload explicitly passed `SS_EMBED_PROVIDER=cpu` (`allocation-workload.json`), yet the live allocation stack contains `onnxruntime::CoreMLExecutionProvider::Compile` and CoreML execution. The current `ss/src/embed.rs:614-625` CPU branch returns an empty provider list. Fastembed passes that list to ort (`fastembed-7.5.0/src/common.rs:473-477`); ort's `apply_execution_providers` iterates only registered entries (`ort-2.0.0-rc.15/src/ep/mod.rs:334-359`), and ort also applies environment providers before session commit (`ort-2.0.0-rc.15/src/session/builder/impl_commit.rs:162-166`). Ort `session/builder/mod.rs:117-123` sets `AutoDevicePolicy::MaxEfficiency` by default when api-22 is enabled; `session/builder/impl_options.rs:351-356` states that on macOS this policy registers CoreML automatically, while PreferCPU prevents automatic provider registration. Thus an empty provider list does not itself suppress ort automatic selection. The captured CoreML allocation stack is consistent with that default; the exact runtime selection call was not separately traced. The environment value is recorded, but the effective Settings value was not separately instrumented. No production process was touched.
